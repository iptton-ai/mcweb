## 0. 背景与定位

- **为什么做**：模组调研结论——「可运行的机械」是头部模组（Create/AE2/Botania）共同的乐趣内核；
  本作红石组已验证「状态编码进 ID + 边沿驱动负载」的模式，阶段一（活塞）补上「方块移动」。
  阶段二补上「持续动力 + 加工机器」，玩法闭环变成：**水车 → 轴/齿轮传动 → 粉碎轮/机械锯加工**，
  与原版红石（阶段一）并行的第二条自动化科技线。
- **阶段一交付**（本方案的地基，动工时以代码为准）：`js/piston.js`（活塞 104 / 粘性活塞 116 / 活塞头 128 /
  观察者 135，0.15s 动作队列 `updatePistonTick`），粘液块（ID 见 config.js）。
  阶段二复用它的：**动作队列模式、贴面朝向放置、popUnsupportedRedstone 连锁脱落、分帧重建预算**。
- **旧机械组的教训**（git 历史：41a7917 加入齿轮 → dd21ea7 随红石组重做移除）：纯装饰性旋转（齿轮只会转、
  没有玩法产出）没有价值。阶段二每个动力元件都必须回答「它让玩家造出什么」——水车是产能，
  轴/齿轮是布线，粉碎轮/锯是产出。**先做终端机器的配方乐趣，再做传动花样**。

## 2. 阶段二总览：玩法闭环

```
水车（ lakes/海边，顶面接触水 → 8 RPM、+64 SU 容量）
   │ 同轴相邻
   ▼
传动轴（轴向直线布线，1:1 传速）
   │ 垂直轴相邻（仅齿轮可换向，啮合反转）
   ▼
齿轮（换向 / 分流）
   ├─→ 粉碎轮（成对，投料口投方块 → 1.2s 碾碎 → 掉落物产出，四级粉碎链）
   └─→ 机械锯（朝向方块自动开采，原木→木板×4）

应力预算：Σ容量(水车) vs Σ负载(粉碎轮32/锯24)；超载 = 整网停转（Create「过载」）
```

机器产出 = **物品实体**（弹出、磁吸、自动入包）——本阶段新增的共用基础设施（§8）。

## 3. ID 编码与方块清单（config.js）

轴向编码约定（区别于红石组的 6 向挂靠面，传动只用 3 轴）：
`AXIS_X=0(东西) AXIS_Y=1(上下) AXIS_Z=2(南北)`，配 `FACING_NORMALS` 同款的轴法线表。

| 方块 | 常量与编码 | 变体数 | 放置规则 | BlockInfo 要点 |
|---|---|---|---|---|
| 传动轴 | `SHAFT_BASE=148 + axis` | 3 | 任意空格 | solid、customMesh、hardness 0.8/axe |
| 齿轮 | `COGWHEEL_BASE=152 + axis` | 3 | 任意空格 | 同上（hardness 1.0） |
| 水车 | `WATERWHEEL_BASE=156 + axis` | 3 | 轴向任意，建议贴水 | 大体积 prop（视觉放大到 1.6 格厚 0.4，允许视觉越界） |
| 粉碎轮 | `CRUSHER_BASE=160 + axis` | 3 | 需两格水平相邻配对（求解时判定，见 §6） | solid、customMesh |
| 机械锯 | `SAW_BASE=164 + facing(0..5)` | 6 | 朝向=被锯方块方向，复用 `FACING_NORMALS` | solid、customMesh |

物品代表变体与 `HotbarBlocks` 注册照阶段一活塞的写法（`SHAFT_ITEM_ID = SHAFT_BASE` 等），
插在红石灯后、工具前。生存开局套装追加：水车×2、轴×16、齿轮×8、粉碎轮×2、机械锯×1（数量可调）。

数值常量（集中 config.js 便于调平）：
`WHEEL_RPM=8`、`WHEEL_SU_CAPACITY=64`、`CRUSHER_SU_LOAD=32`、`SAW_SU_LOAD=24`、
`CRUSH_SEC=1.2`、`SAW_SPEED=6`（等效铁镐速度，喂给挖掘耗时公式）。

## 4. 动力网络求解器（新模块 js/kinetic.js）

骨架照 `updateRedstoneNetwork()`：**事件触发的全量重算，输出派生态到运行时 Map**。

```
updateKineticNetwork():
  1. 全图扫一遍收集动力方块（谓词 isKineticId）——O(1M) 几 ms，与红石同级，事件触发可接受
  2. 邻接规则建图：
     · 同轴相邻（沿轴向连线）：shaft↔shaft/cog/wheel/crusher/saw(朝向轴) —— 同向传递
     · 垂直轴相邻（两齿轮，轴互相垂直）：cog↔cog 啮合 —— 方向取反（换向/分流）
     · 平行轴并排：不连接（避免歧义，对齐 Create 直觉）
     · 水车/粉碎轮/锯 与齿轮同轴相邻也接通
  3. 连通分量求解（BFS，从水车出发）：
     · RPM：全网 = WHEEL_RPM（多水车不加速，对齐 Create）
     · 方向：沿邻接传播，啮合翻转；同一格被相反方向到达 → 「卡死」整网停转
     · 应力：容量 = Σ水车 ×64；负载 = Σ粉碎轮32 + Σ锯24；负载>容量 → 「过载」整网停转
     · 无水车的分量 = 无动力（静止）
  4. 回写派生态：kineticMap: Map<cellKey, {rpm, dir, axis, compId}>
     + components: Map<compId, {capacity, load, overstressed, jammed, hasWheel}>
```

**触发点**（在既有触发旁加一行调用，不碰 setBlockSafe 避免循环）：
放置/破坏动力方块（interaction.js，红石调用的同位）；活塞动作涉及动力方块
（piston.js 动作执行后已调 updateRedstoneNetwork 的地方旁）；助手施工完成（buildQueue.js 完成回调）。
读档后 `initKinetic()` 全量重算（照 `initRedstone` 的挂点）。

**状态查询**：准星对准动力方块 → HUD 提示 `转速 8 RPM · 应力 32/64` 或 `⛔过载`/`⛔卡死`
（挂 js/highlight.js 或 ui.js tooltip，照拉杆提示的做法）。

## 5. 旋转渲染层（不动区块网格）

- 所有动力方块 `customMesh: true`：区块几何跳过（chunk.js:340 现成逻辑），走 propMesh。
  - 轴：细长木杆（0.3×1×0.3 沿轴向）；齿轮：圆盘 + 齿（用 CylinderGeometry 做轮体 + 8 个小齿 box）；
    水车：大圆盘带辐条与叶片；粉碎轮：带凹槽的厚重轮盘；锯：圆锯片。
  - 按 axis/facing 预构建进 `getPropMesh` 缓存，clone 时在 `userData` 挂 `{ spinAxis, cellKey }`。
- **动画 tick** `updateKineticTick(dt)`（挂 main.js 红石 tick 旁）：
  遍历 `state.droppedItems` 中 `prop:true` 且带 spinAxis 的网格，
  `mesh.rotation[spinAxis] += rpm × dir × SPIN_VIS_FACTOR × dt`（8 RPM 肉眼舒适慢转，系数实测调）。
  过载/卡死/无动力 → 不转。position 永远不动 → **零 rebuildChunk**。
- 粒子点缀（可选后置）：水车溅水、粉碎轮出屑——复用 js/particles.js。

## 6. 终端机器 A：粉碎轮

- **配对判定**（求解阶段做）：两粉碎轮水平相邻、轴向相同、连线方向垂直于该轴 → 成对工作；
  单只不成对 → 静止无功能。
- **投料口** = 两轮各自上方格。玩家右键把方块「放置」进投料口（天然支持，零新交互）；
  方块落在投料口 → 开始处理。
- **处理**：投料口有可粉碎方块且所属网络正常转动（rpm>0 且未过载未卡死）→ `CRUSH_SEC=1.2s`
  倒计时（粒子+音效）→ 方块消失 → 按 `KINETIC_RECIPES` 产出**物品实体**（§8）弹出在轮上方。
  无玩家在场照常工作，产出落地待拾取。
- **配方表**（config.js 纯数据，四级粉碎链是核心乐趣）：

  | 投入 | 产出 |
  |---|---|
  | 石头 | 圆石 ×1 |
  | 圆石 | 沙砾 ×1 |
  | 沙砾 | 沙子 ×1 |
  | 玻璃 | 沙子 ×1 |
  | 原木/树干 | 木板 ×4 |

  不在表内的方块 → 投不进去（放置时 toast 提示「这个方块不能粉碎」）或原样吐出，实现时择一（推荐前者）。

## 7. 终端机器 B：机械锯

- 朝向格（`SAW_BASE + facing` 的法线邻格）有方块且网络正常 → 按挖掘公式推进：
  耗时 = `hardness × 1.5 ÷ SAW_SPEED`（等效铁镐，复用 js/mining.js 的 `getBreakSeconds` 思路但不依赖玩家准星）。
- 完成 → 方块消失 + 掉落映射照原版（石头→圆石）；**原木/树干特例 → 木板×4**（锯切转换）。
  产出同样走物品实体。进度表现用粒子（玩家的裂纹 overlay 绑定准星，不复用）。
- 朝向格变化（被挖/被推/变空气）→ 进度重置；挖完不自动寻找下一个目标。

## 8. 共用基础设施：物品实体 + 自动拾取（新模块 js/items.js）

当前生存掉落是「直接进背包」，`state.droppedItems` 只是装饰网格。机器产出需要真正的掉落物：

- `spawnItemDrop(x, y, z, itemId, count)`：0.25 尺寸小立方（图集 UV，复用 js/viewmodel.js
  持方块小立方的构建器），自旋 + 上下浮动 + 简单重力（落地即停，不做碰撞弹跳）。
- **拾取**：玩家 1.5 格内自动入包 + 弹跳音效；机器产出 4 格内磁吸飞向玩家（手感优先）。
- 寿命 120s 上限防堆积；`updateItemDrops(dt)` 挂主循环（enemies 更新旁）。
- **明确不做**：玩家挖掘掉落改走物品实体——改动大且动摇阶段一已验证的行为，留给以后单独立项。

## 10. 与 Create 的差异（v1 简化决策记录）

- 无变速箱/大齿轮/变速 —— 全网 1:1，只有齿轮换向反转。
- 无应力表 UI，网络状态用准星提示承载。
- 无液体流动：水车 = 顶面接触静态水（湖/海里泡着转）。可选放开：把 WATER 加进创造物品栏
  （静态水方块，无模拟代价），让玩家自由选址造水车 —— **推荐做**，一行 HotbarBlocks 的事。
- 机械锯不连锁砍树；粉碎轮投放口是「上方格」而非夹缝。
- 旋转无加速曲线（通电即到速）；红石不控制动力网络（不做 Create 的 redstone links）。
- 多水车不叠 RPM 只叠 SU 容量（对齐 Create 主行为）。

## 11. 存档与性能

- **存档零改动**：动力方块 ID 只含轴向/朝向；网络、转速、机器进度全是派生态，读档 `initKinetic()` 重算
  （机器进度不保存，对齐「瞬时实体不存档」惯例）；物品实体不存。
- 性能：求解器全图扫与红石同级（事件触发、几 ms）；动画 tick 每帧只改几十~几百个 prop mesh 的
  rotation（无 GPU 资源增删）；drawcall 随动力方块数量线性涨（每格一个 Group）——百级齿轮时留意帧率，
  超了再考虑 InstancedMesh 合批（后置优化，不进 v1）。

## 12. 验证清单（E2E，参照红石组/阶段一手法）

1. 水边放水车 → 转；顶面无水 → 不转。
2. 轴直线串联 → 全转；齿轮垂直换向 → 反向转；平行并排齿轮 → 互不连接。
3. 两水车同网 → 应力容量叠加（提示 64→128）；粉碎轮+锯同网超载 → 整网停转+提示。
4. 反向冲突（两路传动汇于一轴）→ 卡死停转。
5. 粉碎轮投石头 → 1.2s → 圆石掉落物弹出 → 走近磁吸入包；四级链 石→圆石→沙砾→沙 逐级可碾。
6. 原木投粉碎轮 / 机械锯锯原木 → 木板×4；锯锯石头 → 圆石。
7. 朝向格被第三方破坏 → 锯进度重置不误伤。
8. 活塞推动轴/齿轮 → 位置更新后网络重算正确（推动后转或不转均需与拓扑一致）。
9. 存档往返：动力方块位置与轴一致，读档后网络转速恢复；机器进度归零（预期内）。
10. 性能：100+ 轴齿轮的网 60fps；水车泡湖里过夜无内存增长（propMesh clone 泄漏专项，
    参照内存泄漏审计的手法查 disposeChunkProps 清理路径）。
11. 红石/活塞回归：时钟、反相器、自动门、飞行器全量不回归。

# 阶段三（可选）：真·装置 Contraption — 设计草案

> 定位：Create 的灵魂体验（轴承带着整面结构旋转、结构整体平移、玩家站上去被带动），
> 也是唯一需要**改动主循环顺序与物理假设**的部分。**不满足门槛判据不动工。**

## 门槛判据（阶段一/二落地后回答）

1. 玩了活塞自动门 + 粉碎链后，是否产生「想造更大的机器」的真实冲动？
2. 性能余量：动力网络重算频率与动力 prop 的 drawcall 是否还宽裕？
3. 载人是否必要？——若主要价值是观景（风车/转台），可先做 **3a 纯观景版**（不载人、零物理改动，
   工作量约 1/4），验证视觉乐趣后再决定 3b。

## 架构四件套（新模块 js/contraption.js + 各处接线）

1. **结构注册表与实体化**：激活时把结构方块从 world 抽出（`cells:[{x,y,z,id}]` 全部写 AIR，
   脏区块一次性 rebuild），构建**一个** THREE.Group——每格一个小立方 mesh（复用 viewmodel.js
   的方块立方构建器，图集 UV），整体 add 进 scene。结构判定 v1 = 从轴承面开始 BFS 实心连通块
   （上限 256 格；上限或连通性失败 → 拒绝激活 + toast），不做 Create 的胶水/超级附着物。
2. **插值动画**：`updateContraptionTick(dt)` 每帧设置 Group transform——
   旋转式（轴承）：绕轴承轴以网络 RPM 旋转，**永续不写回**（风车），停机时对齐最近 90° 再写回；
   平移式（机械活塞/电梯）：起点→终点插值，到位后把 cells 写回 world（批量 setBlockSafe +
   rebuild + 红石/动力网络重算——照活塞动作的重建预算）。
3. **载人物理（仅 3b）**：主循环顺序改动——机械位移必须发生在 `updatePlayerPhysics`
   （main.js:75）**之前**（当前无任何子系统在物理前改方块，这是新的顺序约定，需注释钉死）；
   玩家 AABB 与结构当前占据格相交 → 叠加载具速度（旋转式 = 切向速度 ω×r；平移式 = 结构位移/dt），
   playerPhysics.js 逐轴碰撞只认静态 blocks 的假设需加一个「载具速度注入」入口。僵尸可选，v1 不带。
4. **存档规则（关键决策）**：存档时正在动画中的结构**吸附到最近网格写回 world** → 存档格式零改动，
   读档后由轴承方块重新激活。物品/实体/进度不存，惯例不变。

新方块：`MECHANICAL_BEARING`（ID 从 SHAFT 段之后顺延，6 向 facing，右键贴面结构激活/停；
需接入动力网络作为负载，SU 负载 = 结构格数 ×2）。

## 风险与坑

- 旋转结构以非 90° 角存在时与体素世界的碰撞**无法精确体素化**——3b 载人只能用近似
  （结构包围盒/占格投影），调校成本高，这正是先做 3a 的原因。
- 大结构写回的 rebuild 风暴（N 格结构跨多区块）——复用 buildQueue 的分帧预算思想。
- 内存：结构 Group 的每格 mesh + 材质共享（参照僵尸原型 clone 共享的经验，避免逐格独立材质）。
- 工作量预估 1000+ 行 + 大量手感调校，**必须独立会话、独立提交线**，建议 3a → 3b → 3c（平移结构）三步走。
