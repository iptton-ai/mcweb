## 1. 文章内容拆解

### 1.1 它分析了什么

研究对象是 **deepseek-ai/deepseek-harness 自身的开发过程**（2026-06-10 ~ 2026-08-13，64 天）。核心命题：

> 「一人架构 + 一支 AI 代理舰队 + 人工审查」驱动的真实生产项目——约 90-95% 代码由 AI 代理生成；治理体系本身是为「不可靠但可被机制约束的智能执行者」设计的。

它引 ADR 0007 原文作为哲学支柱：

> 「本代码库主要由编码代理开发。代理对强制门禁的遵从远高于对散文约定的遵从；当代理承担劳动时，'工作量很大'不构成成本论据。」

### 1.2 五个板块（文章结构）

| 节 | 主题 | 核心论点 |
|---|---|---|
| 一 | **约束 Agent 行为** | 三层同构治理：门禁（机器强制）+ 技能（代理内化）+ 决策记录（有生命周期）。配套「信任边界显式化」「成本纪律双向不对称」 |
| 二 | **并行开发与冲突解决** | 微内核 + 固定扩展面 + 能力缝三元组 + merge-down 高频小步（1,849 次）+ 官方 stack 合并 |
| 三 | **任务状态机** | 笔记四态 / 分支 PR / 技能触发 / 简化候选 / 事故，五套状态机 |
| 四 | **孪生实现** | 用两个真实实现防「默认实现变成事实标准」；深挖 LLM 适配器孪生 |
| 五 | **可移植性清单** | 分「任何团队都能用」与「AI 密集型团队才划算」两档 |

### 1.3 它给出的机制清单（这些是文章的真正价值）

- **反过度开发**：`Require a current owner and need` / `Inverse smell`（公共方法只有一个内部调用者=接口泄漏）/ `Require evidence for public choices` / `foundation over blast radius`
- **不变式双层**：静态层（每包 `invariant.ts`）+ 运行时层（companion 插件做**关系性断言**）
- **事故闭环**：subtle + systemic + costly → postmortem → 规则 → 门禁（4 份 postmortem 全部催生门禁）
- **AI 特有坏味道专项治理**：CoT 泄漏 8 类、doc slop 字数预算、AI 环境盲区
- **证据链纪律**：GUI 改动必附 GIF，且必须录自该 PR 自己的分支树
- **双语三元组**：`foo.md`/`foo.zh.md`/`foo.i18n.yaml` + 专属 git merge driver

## 2. 分析方法拆解（它到底是怎么得出结论的）

### 2.1 主导分析动作：四步映射

文章的**主导推理模式**是一个可复用的四步式：

```
治理问题（Agent 会怎样失控）
   → 机制（仓库里有什么规则/脚本/技能）
      → 证据（数字或引文）
         → 可移植结论（你能抄什么）
```

以「过度开发治理」为例：
- **问题**：「AI 代理的默认倾向是为未来的消费者提前建抽象、建注册表、建双表示」
- **机制**：`packages/AGENTS.md` 四条规则 + `dsh-find-simplifications` 证据驱动删除流程
- **证据**：48 篇 simplification 笔记，SessionSummary/ImageBlock/Cron 等整组删除
- **结论**：§5「机械门禁优于散文约定」

这个四步式在文章里重复了十余次，是它最主要的组织骨架。

### 2.2 六类证据来源

审查发现文章的证据来源可分为六类，但**引用纪律严重不对称**：

| 证据类型 | 引用纪律 | 说明 |
|---|---|---|
| ADR / 笔记原文 | **好** | 唯一标「原文」处逐字引了 ADR 0007 英文原句 |

| **git 统计** | **零** | 裸数字，无命令、无口径、无 hash |
| **作者推断** | 未标注 | 最重的结论（「设计了一切」）是推断，但写成陈述 |

**关键事实：全文没有一条 git 命令、没有一个 commit hash、没有一段 `git log` 输出。** 能追溯到的最细颗粒度是「6/13 笔记《twin-llm-adapters》」这种**文件名级引用**——那是文件系统，不是 git 历史。

### ❌ 5 处误述（文章把「条件纪律」或「相邻机制」写成了「普查事实」）

**① 「JSONL vs SQLite 双持久化后端验证抽象」——错（类别错误）**

`dsh-session-persistence/README.md:32` 明写：

> The seam ships the **JSONL** backend... A third-party backend **may** implement the service directly.

SQLite 包是**另一条缝**：`dsh-session-query-sqlite` 是 `ctx.sessionQuery` 的 FTS5 搜索后端，其 README:87 明确禁止当作存储：

> **Derived index, never the source store.** ... the session-persistence database is never opened here.

- **真相**：持久化缝**只发运一个后端**；SQLite 实现的甚至是**另一个抽象**（搜索），且以**消费者**身份坐在缝的另一侧。
- **但**：文章想表达「缝被设计成可换后端」是对的，只是「第二个后端已发运」错了。

**② 「每个包都存在 `src/invariant.ts`」——错**

实测 **38/288** 个包带 `lib/invariant.js`；`dsh-invariants/README.md:71` 给出真实规则：

> Every other workspace package **omits** the companion and states the package-specific reason in its README.

这条「没有 companion」的免责声明在语料中大量出现（如 `dsh-util-values/README.md:65`、`dsh-output-retention/README.md:112`、`dsh-tool-jobs/README.md:87`）。

- **真相**：这是一条**条件性纪律**（只有拥有可观测事件流/可变数据关系的包才发 companion），不是普查。
- **修正后的说法反而更有价值**：在**发运 companion 的 38 个包里**，形状高度统一（`name` / `inject: ["invariants"]` / `install` / `apply`），且由 `pnpm run verify-package-invariants` 机器校验（拒绝空 installer、漏 reporter、注册名错误等）。

**③ 「34 个 verify-* 门禁」——计数不可证，且文章举的例子不存在**

artifact 内可找到 **13 个**不同 verify-* 字符串（其中约 10 个是真门禁；`verify-stream`/`verify-artifacts` 是 vendored 第三方假阳性）。**但文章标题级举例 `verify-agent-note-format` 全 artifact 命中 0 次。**

- 门禁**概念**成立（`doc-sync` 聚合门禁真实存在于 `dsh-session/lib/types/known-event-types.js:4`），**但「34」与具体成员都无法证实**。
- 另注意：artifact 内**没有** `scripts/` 目录、`.github/workflows/`、lefthook/lint-staged 配置——文章 §3.2 的钩子主张完全依赖仓库访问。

**④ 「笔记四态含 `rejected/`」——`rejected/` 在交付物中不存在**

穷举验证：`rejected/` 路径命中 **0**；558 处 "rejected" 全是无关的运行时散文（如「invalid entries are rejected」）。

- 交互事实：184 篇被链接的笔记中有 501 次 `implemented/`、129 次 `archived/`、27 次 `proposed/` 引用，**没有一条 `rejected/` 链接**。在产品自己的「笔记路径即证据链」约定下，这是**有意义的负面证据**。
- **但不等于证明仓库没有 `rejected/`**——未被链接的笔记在这里不可见。
- **更关键**：文章的四态/四类模型**不完整**——实测是 **3 个生命周期 × 6 个类**，其中 **`bug-fix`（12 implemented + 5 archived）完全不在文章的模型里**。

**⑤ 「11 个开发技能」——artifact 只发运 8 个 SKILL.md，且文章点名的技能全不存在**

## 4. 方法论审查：文章的 6 个结构性问题

独立审查（不依赖产品包，纯文本分析）发现文章有系统性的方法论缺口。按杀伤力排序：

### 4.1 政策 vs 实践：「门禁 AI 绕不过」从未被证明开过火 ⚠️ **最锋利**

文章关于门禁的核心论断是**效力论断**（gates actually fire, and firing changes behavior），但它给的证据全是**效力之外**的：

- 文件存在性（34 个脚本存在）
- 脚本名（名字符合预期）
- 脚本意图描述（脚本要做什么）

**没有一条证据表明某个门禁在某次提交上真的红过，或红过之后行为改变了。**

而文章自己引用了正确的标准：

> 教训（7/19 笔记）：**存在性检查是假测试**（「插件名存在、方法存在」）……真正有价值的是**跨时间或跨可变数据的观测关系**。

**文章引用了这条教训，然后自己犯了它。**

更狠的是现成反例就在文章里：postmortem 0001 讲的是「**178 绿测试 + 100% 覆盖**，ACP 真实连接即崩」——即**门禁全绿而事故照发**。文章把它读成「体系在自我完善」，而没有同时读成「**体系当时是失效的**」。

### 4.2 事后合理化冒充设计哲学

文章反复用「**刻意**」标注机制（「核心刻意最小」「钩子刻意窄」「从一开始就**刻意**基于不同内部机制」），但它自己的时间线反证「响应式」解读：

- 「7/18 起 worktree 链式合并；**7/27** worktree-local-lefthook 解决钩子互踩」——**钩子互踩先发生，7/27 的解法是对它的回应**，可文章把窄钩子写成设计原则。
- 「1,849 次 merge-down」被解释为「integrate early and often 的机械执行」——但 1,849 是**累积观测**，把它当作**原则的落实**，因果方向可能是反的（也可能是「merge hell 发生过一次之后才开始高频 merge」）。

**文章没有提供任何一个「原则先于问题出现」的时间证据**（如「某原则写于 X 日，它要防的事故发生在 Y > X 日」）。没有这种证据，「设计哲学」与「事后追认」无法区分。

### 4.3 归因问题：核心主张是推断，不是测量 ⚠️

「约 90-95% 代码由 AI 代理生成」被放在文首「**核心事实**」栏，此后 300 行再未回到它、再未提供任何证据。它实际上承担**整个论证的前提**。

问题在于它无法从文章所述证据得出：

- **同一批元数据支撑相反结论**：文章用作者字段既证明「6 位人类按领域分工」（崔添翼/imccyu/Huanqi Cao/pku-xht/07akioni/Turtle），又证明「90-95% 是 AI 写的」——**共享证据源却指向相反结论**，文章未做任何区分。
- **自指测量环路**：一个由 AI 大量参与的项目，其提交元数据本身就是 AI 生成的。用 AI 生成的元数据去测量 AI 的参与度，需要外部锚点（代理运行日志、token 消耗账、CI 模型调用记录）才能打破。文章没有提到任何这类锚点。
- **判据缺失**：若判据是分支前缀 `codex/*`——那是**任务标识**，不是**产出者标识**。

**结论：「90-95%」应读作「作者基于工作流形态的推断」，而不是统计量。**

### 4.4 存活者偏差：只看得见活下来的机制

文章的观察面完全由**最终存在于仓库中的东西**界定。被彻底放弃、从未落地的尝试，在这套取证方式下**不留痕迹**。

这直接冲击文章最强的论断——「这套体系……为『执行者不可靠但可被机制约束』这个前提**设计了一切**」。但「设计了一切」只有在能看到**失败清单**时才成立；文章看到的是幸存者名单。

佐证：文章能给出的「被否决」样本只有两类且都很小（9 篇被拒提案、7/4 被拒的字数上限提案）——**这两类都恰好是有制度化留痕的否决**，而最大的一类失败（没进目录、直接被忘掉）被完整排除在样本外。

### 4.5 承重分析缺失

文章把十余条机制平铺并列，但没做**承重分析**：哪些机制拿掉项目会真的崩？

这在「一人架构 + 一支 AI 代理舰队」语境下特别要命。且文章的「一人架构」表述与它自己在 §2.3 列出的 **6 位人类领域分工**存在张力——文章没有处理这个矛盾。

另外，34 个门禁 + 686 篇笔记本身可能是**低效率信号**而非优势信号。文章引用了「治理规则不是越多越好」（7/4），但**整篇的修辞方向（「穷尽」「强制」「必须」「全部」）恰恰是「越多越好」**。

### 4.6 「宣称的方法」≠「实际交付的方法」

| 实际交付 | 占比 | 与宣称的关系 |
|---|---|---|
| **(A) 对仓库文档的转述与归纳** | 绝大部分 | **不是 git 历史分析，是文档阅读** |
| **(B) 若干聚合统计数字** | 极小，全部只给结果不给方法 | **不可复现**，不具备「观察」的可信度 |
| **(C) 作者的综合判断与概念命名** | 贯穿全文 | 作者自己的分析产物，**未标注为推断** |

**核心错配**：标题承诺 **git-history forensics**（从提交历史挖出文档里没写的东西），实际交付的是 **document synthesis**（把仓库已写好的文档整理成叙述）。

文章对 git 历史的使用**仅限于「提供日期」与「提供计数」**，从未用它去**反驳**文档、**发现**文档没写的事。而「发现文档与历史不符」正是 git-history 分析相对于文档阅读的**唯一独有价值**。

**一个反常的细节**：作者的引用纪律在**文档类**证据上执行得很好（标原文、给英文引号），在 **git 类**证据上却降为零。这个不对称暗示这些数字**可能不是作者自己跑的**，而是取自仓库自述或他人转述。

## 5. 这篇文章值得肯定的地方

重新分析不等于否定。文章有真实的、不常见的优点：

1. **机制优先于口号** —— 不停留在「他们重视质量」，而是给出「三层同构治理」的具体载体与例子。
2. **唯一一处四要素齐全的一手引用** —— ADR 0007 同时做到：指明文件与标题、标注「原文」、逐字引用（含英文原句）、引文直接支撑中心论点。
3. **给出机制产生的具体技术后果** —— §4 的四条协议分歧（usage 必须在 finish 前发出、finish 后不得再有事件、arguments 全程原始 JSON 字符串、两条合法错误路径）是全文取证质量最高处，且**已被我一手证实**。这是罕见的「机制 → 可验证技术后果」链条。
4. **成本明账** —— 明说孪生实现「适配器 + 带密钥 e2e 维护量翻倍」，不粉饰。
5. **可移植性分档** —— 区分「任何团队都能用」与「需 AI 密集型团队才划算」，这是负责任的知识转移。
6. **注意到治理体系自身会犯错** —— 「规则自身也接受简化审计」「治理规则不是越多越好」。
7. **引用了仓库自己承认的测量局限** —— 「this decision does not claim benchmark measurements」。**值得肯定，但文章没有用同样的标准要求自己。**

## 6. 重新分析的正确做法（如果要做这件事）

文章若要升级为真正的 git-history 分析，最小充分做法：

### 6.1 先交测量协议，再交结论
把「AI 生成占比」的定义写清：
- **归因信号** = 分支前缀 / commit trailer / 作者映射 / 代理运行日志 / token 账？
- **粒度** = commit 数 / diff 行数 / 净增删行数？（agent 倾向大量重写，不同粒度差异极大）
- 无锚点时**公开放弃**强主张。

### 6.2 公开全部查询与分母
至少让「11.4%」与「123 分钟」可以**互验**（前者乘分母应给出后者的上界关系）。文章不给分母，两个本应互为约束的数字无法互相约束。

### 6.3 把门禁**效力**当研究对象，而不是把存在当证据
抓取：门禁历史失败率 / 上线前后同类缺陷率 / `--force` 绕过或临时禁用记录 / postmortem 中「本该挡住但没挡」的条目。
**对门禁本身也要用「存在性检查是假测试」这条标准。**

### 6.4 做承重分析 + 找反事实
对每个机制问「拿掉它会怎样」，并尽量找到反事实证据（机制设立之前是否已发生过它要防的事故）。

### 6.5 显式列出不可见的东西
明确声明失败方案、未留痕的尝试、被放弃的机制**不在样本内**，并说明这对结论强度的限制。

### 6.6 推断与陈述在文本上分开
对每条一手引文标注出处与日期；作者推断用独立标记。

### 6.7 降级全称判断
把「设计了一切」「永远被隔离」「清醒地区分」改为带条件与限定的表述。

## 7. 对「deepseek-harness agentic 研发流程」的重新理解

把文章的素材与我的对拍合起来看，DSH 的 agentic 研发流程实际上是**三层结构**，而文章把它们混在了一层叙述里：

```
┌─ 第一层：产品内的机制（可从交付物验证）★ 文章最可信的部分
│    孪生适配器 / 包自有不变式 / 流协议不变式 / 微内核依赖纪律
│    → 这些是「已发运的工程事实」，产品自己文档化了
│
├─ 第二层：仓库内的治理（需仓库，但形状可验证）
│    Agent Notes 四态 / 双语哈希配对 / verify-* 门禁族 / postmortem 制度
│    → 文章描述了正确形状，产品包通过「引用」间接佐证
│
└─ 第三层：流程统计与叙事（需 git/CI，且需自证口径）
     12,293 提交 / 90-95% AI / 48 篇简化笔记 / 1,849 merge / 并行度
     → 文章最弱的一层，却承担了最强的结论
```

**最关键的重估**：文章的核心哲学命题（「为『执行者不可靠但可被机制约束』这个前提设计了一切」）**在方向上是可信的**——产品里确实存在大量「约束代理行为」的机制，且它们**不是摆设**（不变式真的在运行时抛错、`verify-package-invariants` 真的会拒绝空 installer）。但「**设计了一切**」这个全称判断、以及「**清醒地**区分早有晚」这个意图归因，**超出了任何单项目 n=1 观察所能支撑的范围**。

**更准确的表述**应该是：

> 一个 AI 密集开发的项目，把「对不可靠执行者的约束」从散文约定**机械化为门禁 + 技能 + 有生命周期的决策记录**，并在交付物中保留了可验证的痕迹（孪生实现、包自有不变式、流协议不变式）。其治理体系在**机制层**是真实且文档化的；至于这些机制是**预先设计**还是**事故驱动逐步补齐**，现有证据支持后者更多。
